# ModelDesk 2.16：任务记忆与成员交接

调研与代码核对日期：2026-11-01。本说明记录设计依据和本轮改动；测试、桌面安装及真实服务验收以发布记录为准。

## 从用户工作出发

用户交给一个项目群一项工作，之后补资料、改要求、审阅和继续。平台应保留原始目标，把修改追加到同一任务；后续修改覆盖冲突要求，未改变的要求继续有效。失败的改稿不能清空此前底稿，生成成功的图片也不能因为正文汇总失败而消失。

成员各自完成一段工作。写作者产出原稿，审阅者可能只写修改意见，创作者仍需要原稿和意见。交接应按计划中的依赖关系传递实际成果，避免把无关并行分支混入。最终编辑和审查者需要完整成品及执行证据，才能判断交付是否满足要求。

## 业务对象

| 对象 | 保存什么 | 不能据此声称什么 |
| --- | --- | --- |
| 任务记忆 `task_context` | 当前项目、群和任务边界；用户要求序列、最近底稿、失败修改前的完整稿、资料与媒体来源 | 摘要存在不代表文件仍可读，也不代表模型理解或执行了要求 |
| 冻结输入 | 用户已选择的附件副本、文本边界、资料指纹；不重新打开任意本机路径 | 历史附件中的指令不能增加权限 |
| 步骤及依赖 | 成员、职责、直接依赖、尝试、实际输出与子任务身份 | 审阅意见不能替代原稿；完成一个分支不等于整项任务完成 |
| 交接回执 `input_context` | 用户要求数量、记忆指纹、直接及间接上游、输出指纹、参考素材 ID、实际准备的提示词指纹与长度 | 回执证明输入已准备，不证明外部服务已经接收或成果通过验收 |
| 成果与版本 | 完整正文、真实媒体清单、版本、审查与缺失项 | 模型声称“已生成”不能替代文件读取和校验 |

## 数据如何流动

```text
当前要求 + 同一任务的历史要求 + 已选资料副本
    → 冻结任务记忆与成员配置
    → 形成验收要求和步骤依赖
    → 每个成员取得本步骤要求、完整依赖链成果及适用资料
    → 保存交接回执，再调用原有模型或执行 Agent
    → 保存实际输出和媒体，组合完整成果并审查
    → 展示成品与缺失项；继续时复用已完成步骤和已保存派发内容
```

用户选择“开始新任务”时建立新的记忆边界，旧记录仍可查看。任务资料与模型的一次输入窗口分开管理：完整记录保留在本机，原生 Agent 的有限交接窗口优先保留用户要求和必要前置稿；背景整理无法满足预算时明确失败，不把截断稿当作完整输入继续派发。

## 本轮修正对应的问题

| 已确认的问题 | 2.16 的处理 |
| --- | --- |
| 只有图片或视频、正文为空的历史任务，其媒体未进入记忆；后来的纯文本修改也会遮住较早媒体 | 媒体独立于正文收集，在同一任务边界按内容去重；仅保留底稿所需的旧链接来源，复用后重新校验归属和真实字节。网页和离线 ZIP 都映射到当前副本 |
| 历史附件去重只筛选了 ID，却再次拼入整份旧附件包及旧项目说明 | 按冻结清单的路径、指纹和字符边界提取尚未提供的文本，排除重复附件与旧项目头信息 |
| “原稿 → 审阅意见 → 创作”只传直接上游，创作者失去原稿 | 稳定遍历完整祖先依赖，去重并排除无依赖的并行分支；未完成祖先阻止交接 |
| 上游完整输出在最终编辑或审查前再次被字符切片 | 自动协作链路传递完整输出、完整修订底稿和完整待审正文；供应商长度失败仍按失败处理 |
| 用户无法看出成员实际得到哪些要求和前置成果 | 每步保存并显示 `input_context`；原生步骤继续时保留原派发提示词与回执，不将重试伪装为新的输入 |

模型步骤还会读取并校验上游生成的图片，将缩略图作为实际图片输入；回执区分清单引用、模型图片输入和原生 Agent 参考图。模型单步骤最多接收 8 张图片（含用户附件）；超过时明确停止。绘图步骤没有因此获得图片编辑能力，视频全片审阅也不在此改动范围。

这些是输入完整性与可追溯性的改进，不能保证模型必然遵循全部要求。针对性回归需要覆盖媒体单独成功、附件重复、三角色依赖链、无关并行分支、长稿尾部内容以及中断后继续。

## 架构取舍与运行边界

本轮保留 Python / Pydantic 契约、现有 JSON 持久记录、`JobManager`、自动协作依赖调度器及原有执行适配器。显式 LangGraph 流水线继续由 `RunStore` 持久化；自动项目群由自己的任务记录保存状态。本轮没有启用 LangGraph 原生 checkpointer，也没有迁移为多机数据库工作流。

改动集中在 `task_context.py` 的任务记忆、`attachments.py` 的冻结文本选择、`coordination.py` 的依赖交接和完整成品输入，以及前端的记忆清单与回执展示。应用上述设计思路并自行实现这些修正，不新增软件依赖或第三方代码许可；已有依赖的许可证义务继续保留。

本机 Muse 与官方产品的持久云电脑有实际区别：依赖本机、应用登录和可操作窗口；锁屏、应用状态、网络及原生控制失败都可能中断工作。保存输入与恢复身份不代表电脑关闭后仍会执行，也不能保证已经提交的外部动作可撤销。文件是否生成、能否读取、是否通过检查应分别展示，不能只依据聊天中的成功声明。

后续若确实需要多机 worker、自动租约恢复或跨设备执行，应先统一现有任务身份、状态迁移与副作用去重，再评估数据库或托管执行层；不在当前上下文修复中引入第二套权威状态。

## 本轮实测记录

2026-11-01，通过现有已登录网关运行 GPT `gpt-6.1-sol` 与 Gemini `gemini-3-flash`，三角色为写作者、审核者、交付编辑。第一轮要求《纸船的约定》、小禾、红色纸船、三个指定小节和固定末句；第二轮只要求改成蓝色，同时将滚动历史设为 1 轮。两轮均完成三个依赖步骤和最终审查。两版成品各含 207 个汉字，逐字比对只改变两处颜色词，其他正文完全一致。编辑的交接回执包含原稿与审阅意见两份上游成果，第二轮任务记忆保留两条完整用户要求。

浏览器已点击验证交接来源、任务记忆、新任务隔离提示及右侧最终正文。工程测试另外覆盖二十轮媒体去重、受损素材拒绝、原生派发重试不重复前置步骤、长稿尾部、真实本地 PNG 输入，以及带旧图链接的离线 ZIP。此轮没有重新调用 Muse 创作或生成云端图片；这些原生和媒体边界以回归测试及现有文件检查为证，不代表新一次云端创作已验收。

本机详细记录保存在 `data/acceptance-216/`（不提交用户运行数据）；软件全量检查与桌面打包由全局 Git 完成工具执行并保留日志。
